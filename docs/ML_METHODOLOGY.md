# Machine Learning Methodology and Model Governance

## Current deployed baseline

The repository currently ships a deterministic Ridge regression demonstration model. Its training data is generated by `synthetic_training_frame()` in `backend/app/ml/predictor.py` using a fixed random seed. The generated target is a formula with random noise; it is not collected from real students or an authorized institutional dataset.

The feature set includes study hours, previous marks, attendance, assignment scores, class participation, homework completion, sleep hours, extracurricular participation, internet access, and family support.

The target is a bounded synthetic score. The training pipeline uses an 80/20 train/test split with a fixed seed, StandardScaler, and Ridge regression. Metrics returned by the administrator model endpoint are measured on that held-out synthetic test split.

**Interpretation restriction:** these metrics and predictions demonstrate software integration and a reproducible ML workflow only. They must not be described as validated forecasts for real students or used for high-stakes academic decisions.

## Model-compatible explanations

`GET /api/predictions/{prediction_id}/explanation` decomposes a saved prediction using the Ridge model artifact version recorded with that prediction. Each feature contribution is the fitted Ridge coefficient multiplied by the standardized feature value relative to the training mean. The intercept is returned as the baseline. Contributions add to the raw model output before clipping to the supported 0–100 score range.

This is a model-specific linear decomposition, not SHAP. It describes how the model calculates its output; it does not establish causality or prove that changing a feature will produce the same real-world effect.

The endpoint checks prediction ownership and refuses to explain a prediction if the available artifact version differs from the saved prediction version.

## What-if simulation

`POST /api/predictions/simulate` evaluates a baseline and a scenario with the same deployed model pipeline. Both inputs must describe the same subject and semester. The response includes both estimates, their difference, model version, dataset provenance and a disclaimer. Simulations are not persisted as prediction history records.

## Readiness monitoring

- `/api/health` remains backward-compatible for existing deployment checks.
- `/api/health/live` confirms process liveness.
- `/api/health/ready` checks the database connection and model availability. A dependency failure returns HTTP 503.

## Requirements before using real student data

1. Obtain a dataset with documented provenance, permission, and an appropriate consent/legal basis.
2. Verify that the target is genuinely observed academic performance and is defined consistently.
3. Remove direct identifiers and unnecessary sensitive attributes; document retention and access controls.
4. Audit missingness, duplicates, outliers, representativeness, label quality, and potential leakage.
5. Define a split strategy before model selection. For longitudinal or grouped student/institution records, prevent the same entity from leaking across train and test sets.
6. Establish a simple baseline and compare justified models using cross-validation on training data.
7. Fit preprocessing and imbalance handling only within training folds. Do not resample validation or test data.
8. Select the model using validation results, evaluate once on an untouched test set, and report task-appropriate metrics with limitations.
9. Calibrate probabilities before displaying them as probabilities. Do not infer risk categories from regression scores without a validated policy.
10. Version the dataset schema, feature pipeline, model artifact, evaluation report and deployment compatibility contract together.
11. Run shadow or limited pilot evaluation with human oversight before replacing the deployed demonstration model.
12. Never automatically train on production student records or silently replace the live artifact.

## Compatibility contract

The existing prediction endpoint and input schema remain unchanged. The explanation and simulation endpoints reuse the current model artifact and do not require a database schema migration. Existing prediction history remains readable. Any future model replacement must preserve the current input feature contract or introduce an explicitly versioned API/model contract with a migration and compatibility plan.
